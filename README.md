# Herdr 이슈 구현 루프

GitHub 또는 GitLab 이슈를 설계한 뒤, 항목 하나의 구현과 설계 검토를 반복한다.
설계 에이전트는 같은 pane과 대화를 유지한다. 구현 에이전트만 항목마다 새로 생성한다.
정상 중단 후 같은 명령을 실행해도 기존 설계 세션을 재사용한다.
전체 완료 후에도 설계 pane을 남겨 결과를 확인할 수 있다. 필요 없으면 직접 닫는다.
설계 pane이 사라졌다면 새 세션에서 저장된 작업 문서를 읽어 복구한다.
같은 Git worktree의 코드와 작업 문서가 다음 세션에 전달된다.

## 구성

- `run.sh`: 실행 진입점.
- `runner.py`: Herdr 호출, 상태 저장, 중단과 재개 관리. Python 3 표준 라이브러리만 사용한다.
- `references/designer.md`: 최초 설계와 매 구현 결과 검토 지침.
- `references/implementer.md`: 지정 항목 하나의 구현과 결과 기록 지침.
- `SKILL.md`: Claude Code 스킬 정의. 이 저장소를 스킬로 설치했을 때만 쓰인다.

macOS 또는 Linux의 Herdr pane 안에서 실행한다.
사용할 에이전트 CLI와 이슈 읽기용 `gh` 또는 `glab` 인증을 먼저 준비한다.
에이전트의 권한·프로젝트 신뢰 설정은 그대로 사용하며, 승인 창을 자동으로 통과시키지 않는다.

## 스킬로 설치

아래 명령은 선택 사항이다. 설치하지 않아도 `run.sh`를 직접 실행할 수 있다.

설치하면 Claude Code의 모든 프로젝트에서 이 루프를 부를 수 있다.
저장소 자체를 스킬 폴더로 연결하므로 사본이 생기지 않고, `git pull`이 곧 업데이트다.

```bash
ln -s "$(pwd)" ~/.claude/skills/issue-loop
```

새 환경에서는 저장소를 받은 뒤 같은 링크를 만든다.

```bash
git clone <이 저장소 주소> ~/workspace/jaejin-loop
ln -s ~/workspace/jaejin-loop ~/.claude/skills/issue-loop
```

설치 후에는 이슈 번호를 주고 루프를 요청하면 된다. 스킬이 worktree 생성, 경로 조립,
반복 횟수에 맞는 `--max-calls` 계산, 실행 전 점검을 대신한다. 실제 설계와 구현은
그대로 `run.sh`가 띄우는 에이전트가 수행한다.

## 실행

먼저 구현 대상 저장소에서 별도 worktree를 만든다. 기존 작업이 있는 브랜치를 쓸 때는 그 상태를 먼저 확인한다.

```bash
git worktree add ../my-project-issue-123 -b loop/issue-123
```

아래 실행기의 경로는 이 예제를 둔 위치로 바꾼다. 설계는 `claude`, 구현은 `codex`가 기본값이다.
다른 종류를 쓰려면 `--design-kind`와 `--implement-kind`로 지정한다.
둘 다 같은 종류를 사용해도 된다. 종류 목록은 `herdr agent start --help`에서 확인한다.

```bash
/path/to/issue-loop/run.sh 'https://gitlab.example.com/group/project/-/issues/123' \
  --repo /absolute/path/my-project-issue-123 \
  --work tmp/issue-123 \
  --design-kind claude \
  --implement-kind codex
```

이슈는 설계 에이전트가 읽기 전용으로 조회한다. 번호만 전달하면 해당 저장소의 프로젝트를 사용한다.
조회 도구는 worktree의 `origin` 호스트로 정한다. github.com이면 `gh`, 그 외 호스트면 `glab`이다.
주 저장소에서의 무인 변경을 막기 위해 `--repo`에는 별도 worktree만 허용한다.
작업 문서는 `design.md`에 목적과 설계, `tasks.md`에 구현 목록, `progress.md`에 구현 결과를 담는 세 개다.
`runs/`에는 호출별 프롬프트와 에이전트가 작성하는 결과 JSON이 쌓인다.

```text
tmp/issue-123/
  design.md
  tasks.md
  progress.md
  runs/                 # 호출별 프롬프트와 JSON 결과
```

실행 상태 파일은 작업 폴더에 두지 않는다. 구현 에이전트가 `git clean`이나 되돌리기로 worktree를
정리할 때 상태까지 함께 사라지는 것을 막기 위해, 해당 worktree의 Git 메타데이터 폴더에 보관한다.

```text
<주 저장소>/.git/worktrees/<worktree 이름>/herdr-issue-loop/
  state.json            # 단계, 지정 작업, 구현 횟수, 설계 세션 정보
  log.jsonl             # 호출별 한 줄 기록, 시간순
  lock                  # 같은 worktree의 중복 실행 방지
```

`log.jsonl`에는 호출이 끝날 때마다 시각, `run_id`, 단계, 작업, 결과, 소요 시간, 요약이 한 줄씩 쌓인다.
타임아웃이나 검증 실패로 중단된 호출도 `action`이 `error`인 줄로 남는다.
여러 날에 걸쳐 나눠 실행했을 때 어디까지 갔고 어디서 막혔는지 이 파일 하나로 확인한다.

`references/designer.md`와 `references/implementer.md`는 실행 지침이다.
생성되는 설계 문서는 `--work`로 지정한 작업 폴더의 `design.md`에 저장한다.
작업 문서는 자동 커밋하지 않는다. 필요하면 해당 폴더만 로컬 Git 제외 규칙에 추가한다.

## 반복과 제한

기본 실행은 최초 설계 후 항목 하나를 구현하고 설계 검토까지 마친 뒤 멈춘다.
위 실행 명령에 다음 옵션을 추가하여 테스트 범위를 선택한다.

| 옵션 | 새 작업에서 실행하는 범위 |
|---|---|
| `--stop-after design` | 최초 설계만 |
| `--stop-after implement` | 설계 후 첫 항목 구현까지, 결과 검토는 다음 실행으로 남김 |
| `--iterations 3` | 최초 설계 후 구현과 설계 검토를 3회 반복 |
| `--stop-after implement --iterations 3` | 구현을 3회 수행하고 마지막 구현 직후 종료, 중간 검토는 수행 |

`--stop-after` 기본값은 `review`, `--iterations` 기본값은 `1`이다.
횟수는 이번 실행에서 마친 구현 또는 검토 횟수이며, 동일 항목의 보완 구현도 한 번으로 센다.
최초 설계는 반복 횟수에서 제외한다. `--stop-after design`은 `--iterations 1`만 허용한다.
이미 설계가 끝났다면 `--stop-after design`은 추가 호출 없이 종료한다.

설정한 단계에서 멈춘 것은 오류가 아니다. `--resume` 없이 같은 작업 경로로 다시 실행하면
저장된 다음 단계부터 이어간다. 이전 실행이 구현 직후 멈췄다면 먼저 남은 설계 검토를 수행한다.
`review` 기준에서는 이 검토도 이번 실행의 1회로 센다.
전체 완료 또는 실제 오류·승인 대기가 발생하면 지정 횟수보다 먼저 종료한다.

최초 설계 후 `implement`와 `review` 단계를 반복한다.
설계자는 `progress.md`, 코드 변경, 검증 근거를 확인하고 같은 항목의 보완 또는 다음 항목을 지정한다.
설계 변경 시 기존 설계 전체와 완료한 구현의 일관성을 검토한다.
전체 완료는 설계자의 최종 수용 조건 검증 이후에만 가능하다.

별도 제한의 기본값은 실행당 20회 호출, 작업별 구현 최대 3회, 호출당 1,800초다.
`--max-calls`, `--max-task-attempts`, `--timeout`으로 변경한다.
일반 Git·Herdr 명령은 30초 안에 응답해야 한다. 에이전트 응답 대기 명령은 `--timeout`에
통신 여유 30초를 더한 시간으로 제한한다. 제한을 넘으면 실행기가 중단되며, pane의 에이전트는 계속 실행 중일 수 있다.
`--max-calls`에 먼저 도달하면 반복 도중에도 멈춘다. 새 작업에서 검토까지 N회 반복하려면
최소 `2 × N + 1`회의 호출을 허용해야 한다. 예를 들어 20회 반복은 `--iterations 20 --max-calls 41`로 실행한다.
1,000개 작업은 최초 설계 외에도 구현·검토에 최소 2,000회 호출이 필요하다.
호출 횟수 제한에 도달하면 같은 명령으로 계속한다. 작업별 구현 횟수는 실행 간 누적된다.
이 횟수는 결과를 남겨 검토 대상이 된 구현만 센다. 타임아웃이나 중단으로 결과 없이 끝난 호출은 세지 않는다.
같은 worktree에는 한 작업만 실행하며, 미완료 작업이 있으면 다른 작업 폴더로 실행할 수 없다.
앞선 작업을 포기하고 다른 작업을 시작하려면 `run.sh --repo /absolute/path/my-project-issue-123 --release`로
소유 정보를 해제한다. 문서와 호출 기록은 남으며, 같은 작업 폴더로 다시 실행하면 최초 설계부터 시작한다.
해제 전 기존 구현 pane은 종료해야 하며, 설계 pane은 `idle` 또는 `done` 상태여야 한다.
상태 조회에 실패하거나 실행 여부를 확인할 수 없으면 소유 정보를 보존한다.
pane 생성 중 중단되어 ID가 없는 경우에는 남은 pane을 직접 확인하고 `--resume --feedback`으로 복구한 뒤 해제한다.

자동 무한 재시도는 없다. pane 분할 방향은 `--direction right` 또는 기본값 `down`으로 선택한다.

설계 세션이 길어지면 `--design-turns N`으로 호출 N회마다 세션을 새로 시작할 수 있다.
기본값 `0`은 세션을 계속 유지한다. 값을 주면 설계 pane을 닫고 다음 호출에서 작업 문서를 다시 읽으므로,
문서만으로 이어갈 수 있는지 매번 확인하게 된다. 작업 수가 많아 맥락 압축이 걱정될 때 사용한다.

## 중단과 재개

승인 대기, 타임아웃, 잘못된 결과, Ctrl+C 발생 시 자동으로 다음 에이전트를 호출하지 않는다.
생성한 pane과 변경 사항을 남겨 사용자가 확인할 수 있게 한다.
타임아웃은 에이전트 종료를 뜻하지 않는다. 기존 pane에서 작업이 계속되는지 반드시 확인한다.

1. Git 메타데이터 폴더의 `state.json`에서 `pane`을 확인하고 해당 터미널을 본다.
2. 구현 pane은 작업을 확인하고 종료한다. 설계 pane은 유지하되 작업·승인 대기를 해소하여 입력 대기 상태로 만든다.
3. 원래 명령에 `--resume --feedback '확인한 상태와 결정 내용'`을 추가한다.

재개 시 바로 재구현하지 않고 기존 설계 세션에서 실제 코드와 문서를 검토한다.
최초 설계 중 중단됐다면 최초 설계부터 이어가며, `--stop-after design`도 그대로 사용할 수 있다.
기존 설계 세션이 있는 동안에는 `--design-kind`를 바꾸지 않는다.
생성 직후 상태 저장 전에 중단됐다면 pane ID가 누락될 수 있으므로 Herdr 화면도 확인한다.
실행기는 결과 JSON의 호출 ID·단계·작업과 필수 문서 존재를 검사한다. 단계별로 다음을 추가로 확인한다.

| 단계 또는 결과 | 확인 내용 |
|---|---|
| 구현 완료 | `progress.md`의 해당 작업 절 안에 현재 `run_id`의 `### 구현 결과`가 있는지 |
| 검토 완료 | 같은 절 안에 검토 대상 구현의 `run_id`를 적은 `### 설계 검토`가 있는지 |
| `implement` 반환 | `tasks.md`에 `## T-001` 형식으로 그 작업 ID 제목이 있는지 |
| `complete` 반환 | `progress.md`에 `## 최종 검토` 절이 있는지 |

검토 호출에는 실행기가 `git status`로 직접 센 worktree 변경 파일 수도 함께 전달한다.
설계자가 구현자의 보고 대신 이 값으로 범위 이탈을 확인할 수 있다. 작업 폴더는 이 수에서 제외한다.
새 디렉터리 안의 미추적 파일도 각각 센다. 이 값은 현재 항목만의 변경량이 아니라 worktree 전체 누적 변경량이다.

내용의 정확성은 에이전트 검토와 프로젝트 검증에 의존하며 JSON만으로 보장하지 않는다.
정상 인계가 확인된 구현 pane만 자동 종료한다. 사용자의 다른 pane은 종료하지 않는다.

자동 커밋, 푸시, 이슈 댓글, PR·MR 생성, 머지는 수행하지 않는다.
완료 후 변경 사항을 검토하고 대상 프로젝트의 PR 또는 MR 규칙에 따라 제출한다.

## 로컬 검증

```bash
bash -n run.sh
python3 -m unittest discover -s . -p 'test_runner.py'
```
